# gobee

Write Linux eBPF kernel-side programs in Go. gobee transpiles a strict subset of Go into BPF C. You compile that C with clang and load the resulting object the way you would for any hand-written BPF program: `cilium/ebpf` plus `go:embed`.

The Go ecosystem already has solid userspace tooling for BPF. The kernel side has always ended with "now write your program in C." gobee closes that gap. Aya did this for Rust. gobee aims to be the Go-native answer.

## Why transpile, not generate BPF directly

`gc`, the Go compiler, has no LLVM-based BPF backend. Adding one is a multi-year compiler project. `rustc` is built on LLVM and that's why Aya works. So gobee emits C and reuses clang's BPF backend, which gives us mature codegen, BTF, and CO-RE relocations for free.

## Quickstart

```bash
go install github.com/boratanrikulu/gobee/cmd/gobee@latest

cd example/helloworld
make build                     # gobee translate, clang, go build
sudo ./helloworld eth0
```

You'll need clang with the BPF target. On Linux that's the distro package; on macOS, `brew install llvm`. The transpiler itself is pure Go and runs anywhere.

## What gobee writes

Given a kernel-side `.go` file like:

```go
//go:build ignore

package main

import "github.com/boratanrikulu/gobee/bpf"

//bpf:license GPL

var PerIface = bpf.HashMap[uint32, uint64]{MaxEntries: 64}

//bpf:section xdp
func CountPackets(ctx *bpf.XdpMd) bpf.XdpAction {
    var idx uint32 = ctx.IngressIfIndex
    count, ok := PerIface.Lookup(&idx)
    if !ok {
        var one uint64 = 1
        PerIface.Update(&idx, &one)
        return bpf.XdpPass
    }
    bpf.AtomicAdd64(count, 1)
    return bpf.XdpPass
}

func main() {}
```

`gobee translate --bindings-dir ./bpf ./bpf/src` produces three things:

1. `bpf/src/counter.bpf.c`: BPF C ready for clang.
2. `bpf/src/counter.bpf.c.map`: sourcemap so verifier errors map back to Go lines.
3. `bpf/counter_bindings.go`: typed Go accessors for userspace: `bpf.LoadCounter(spec)`, `objs.PerIface.Lookup(...)`, `objs.AttachAll(ifindex)`, your kernel-side struct types and constants re-published.

`gobee` stops here. clang compiles the C. `go:embed` pulls the `.o` into your binary. `cilium/ebpf` loads it at runtime. Same pattern as a handwritten BPF program, just without the C.

## Project layout (typical)

```
yourproject/
├── bpf/                      # Go package, importable from anywhere in your project
│   ├── embed_amd64.go        # //go:embed bin/x86/your.bpf.o
│   ├── embed_arm64.go
│   ├── your_bindings.go      # generated by gobee
│   ├── bin/{x86,arm64}/your.bpf.o
│   └── src/                  # not a Go package; clang lives here
│       ├── your.go           # //go:build ignore: kernel-side source
│       ├── your.bpf.c        # generated
│       ├── Makefile          # clang per arch
│       └── vmlinux.h         # vendored BTF dump
├── main.go                   # imports yourproject/bpf
└── Makefile
```

The split keeps `bpf/` a clean importable Go package (Go rejects `.c` files in non-cgo packages). Kernel sources and clang artifacts live one level down in `bpf/src/`.

## Examples

- `example/helloworld/`: the canonical XDP packet counter, ~40 lines kernel-side, ~80 lines userspace.
- `example/sysmon/`: XDP, two tracepoints, and a kprobe in one binary, sharing a ringbuf for events. Demonstrates per-syscall typed contexts, user-defined helper functions, and the `AttachAll` shortcut.

## Status

Phase 1 (XDP packet counter end-to-end) and most of phase 2 are done. See [`docs/status.md`](docs/status.md) for the full matrix: program types, map types, helpers, CO-RE features.

What works today, briefly:

- 8 program types: XDP, tracepoint, kprobe / kretprobe, uprobe, sock_ops, TC, cgroup_skb, LSM
- 16 map types including ringbuf, perf_event_array, the per-CPU variants, bloom filter, LPM trie, prog_array, and the per-object storage maps (sk / task / inode)
- ~200 BPF helpers auto-generated from libbpf v1.5.0
- CO-RE field reads on kernel structs, direct field access on UAPI BPF context structs
- Typed Go bindings: programs and maps as struct fields, `Load<Stem>`, `Close`, per-program `Attach<Name>`, `AttachAll`
- Kernel-version gate at load time via [bpfvet](https://github.com/boratanrikulu/bpfvet): instead of a cryptic verifier rejection on an old kernel, you get "needs kernel ≥5.8, host is 5.4"
- Verifier-error → Go-source mapping via `gobee diagnose`

## CI

GitHub Actions runs four layers on every push:

1. `go test`, `go vet`, transpiler golden tests
2. Coverage matrix: every map type and `//bpf:section` kind has at least one example
3. clang compile of every curated example, then `bpfvet` portability report
4. Real-kernel verifier acceptance: `ebpf.NewCollectionWithOptions` on each `.bpf.o` (Ubuntu 24.04 runner, kernel 6.x)

The transpiler is type-checked by `go/types` at parse time, validated against the supported subset, then emitted. There is no fuzzy stage.

## Toolchain

- The gobee binary builds anywhere (pure Go, no CGO).
- Compiling `.bpf.o` needs clang with the BPF target. Apple's bundled clang doesn't ship with it; on macOS use `brew install llvm` or build inside a Linux VM.
- Running the artifact needs Linux. Phase 1 targets arm64 + amd64 (both little-endian for BPF).

## Inspirations
