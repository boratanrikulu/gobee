# helloworld: gobee end-to-end example

An XDP packet counter, keyed by ingress interface index. The kernel-side program is written in Go.

The kernel program lives in [`bpf/src/counter.go`](bpf/src/counter.go). gobee transpiles it to BPF C, the Makefile compiles that with clang, and the userspace driver (`main.go`) loads the resulting `.o` via [cilium/ebpf](https://github.com/cilium/ebpf) and attaches it to a network interface. Same workflow as a hand-written BPF program. The only thing that's different is the kernel source.

## Layout

```
helloworld/
├── bpf/                                # Go package, importable from anywhere in this module
│   ├── embed_amd64.go                  # //go:embed bin/x86/counter.bpf.o
│   ├── embed_arm64.go                  # //go:embed bin/arm64/counter.bpf.o
│   ├── counter_bindings.go             # generated by gobee
│   ├── bin/{x86,arm64}/counter.bpf.o   # compiled by clang
│   └── src/                            # not a Go package; clang lives here
│       ├── counter.go                  # ← you write this
│       ├── counter.bpf.c               # ← gobee writes this
│       ├── counter.bpf.c.map           # ← sourcemap for verifier-error mapping
│       ├── vmlinux.h                   # ← kernel BTF dump (see SOURCE.md)
│       └── Makefile                    # ← clang per arch
├── main.go                             # imports example.com/gobee-helloworld/bpf
└── Makefile                            # ties translate → clang → go build
```

The split is deliberate. `bpf/` has to be a clean Go package because everything else in the project imports it. clang artifacts (`.bpf.c`, `.bpf.o`, the kernel source) can't live there because Go rejects `.c` files in non-cgo packages. So they sit one level down in `bpf/src/`, which is just a directory of files as far as Go is concerned.

## Run

Linux only, arm64 or amd64. Needs `clang` with the BPF target plus `llvm-strip`.

```bash
cd example/helloworld
make build                       # gobee translate → clang → go build
sudo ./helloworld eth0
```

What `make build` actually does:

1. `gobee translate --bindings-dir ./bpf ./bpf/src` parses `bpf/src/counter.go`, type-checks it, validates the Go subset, writes `bpf/src/counter.bpf.c`, and writes `bpf/counter_bindings.go` (typed Go accessors for the userspace side).
2. `make -C bpf/src bpf-all` runs `clang -target bpfel -O2 -g -D__TARGET_ARCH_<arch> -c counter.bpf.c -o ../bin/<arch>/counter.bpf.o`.
3. `go build .` picks the matching per-arch embed file from `bpf/`, links the `.o` into the binary via `go:embed`, and produces `./helloworld`.

Output looks like:

```
2026/04/30 12:34:56 attached XDP to eth0, ctrl-c to detach
2026/04/30 12:34:57 packets on eth0: 12
2026/04/30 12:34:58 packets on eth0: 47
```

## How the bindings show up in main.go

The generated `bpf/counter_bindings.go` gives userspace typed access to everything the kernel-side declared:

```go
spec, err := ebpf.LoadCollectionSpecFromReader(bytes.NewReader(bpf.Program))
objs, err := bpf.LoadCounter(spec)        // typed constructor
defer objs.Close()

links, err := objs.AttachAll(iface.Index) // attaches every //bpf:section program
defer closeAll(links)

count, _ := objs.PerIface.Lookup(&key, &val)  // typed map access
```

No `coll.Programs["CountPackets"]`, no `coll.Maps["PerIface"]`. If you rename the kernel-side function, the bindings get a new field name and the userspace caller stops compiling. That's the point.

`bpf.LoadCounter` also runs [bpfvet](https://github.com/boratanrikulu/bpfvet) on the spec before calling `LoadAndAssign`. If the host kernel is older than the program needs, you get `bpf program needs kernel >= 5.8, host is 5.4` instead of an opaque `EINVAL`.

## vmlinux.h

The emitted C uses `BPF_CORE_READ` for kernel-internal struct fields, so it needs `vmlinux.h`. Generate it once on the target kernel:

```bash
sudo bpftool btf dump file /sys/kernel/btf/vmlinux format c > bpf/src/vmlinux.h
```

CO-RE handles cross-kernel portability at load time, so the same `.bpf.o` loads on other kernels too, as long as the fields you read exist there. See [`bpf/src/SOURCE.md`](bpf/src/SOURCE.md) for the version that's currently committed.

## Reproducing across arches

The same `counter.bpf.c` compiles for both arm64 and amd64. This is BPF, not host code. `D__TARGET_ARCH_<arch>` only affects a few macros in `bpf_helpers.h` that need to know the host arch. The matching per-arch Go embed file picks the right `.o` at build time.

## Bootstrapping caveat

`go build` and `go vet` will fail with `pattern bpf/bin/<arch>/counter.bpf.o: no matching files found` until clang has produced the `.bpf.o` at least once. `go:embed` is checked at compile time. Run `make build` (the top-level target chains gobee translate → clang → go build in order) and you won't hit this.

## Verifying the artifact with bpfvet

```bash
bpfvet bpf/bin/arm64/counter.bpf.o
```

Reports the minimum kernel version, the helpers and map types in use, and any portability warnings.
